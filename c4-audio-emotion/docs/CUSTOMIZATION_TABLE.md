# Customization Table — C4

The supervisor allowed pretrained models **as long as I add my own customization**.
This table separates what I **used** from what I **built or changed**.

| Pretrained / existing component | What I changed or added | Why |
|---|---|---|
| **CLAP** audio model (`laion/clap-htsat-unfused`, LAION), used frozen | Built the audio pipeline around it: 48 kHz mono resampling, 10 s windows with 5 s hop, silence padding of the last window, batched embedding. Trained my **own model on top** of its 512-number embeddings (next row). | Training an audio model from scratch isn't feasible with ~1,800 labelled songs; CLAP gives strong general audio features, and my head learns the emotion task. |
| **Demucs** (`htdemucs`, Meta), used frozen | Turned its 4 output tracks into **speech** (vocals) and **background** (drums + bass + other) at 48 kHz mono; my emotion model runs on the background track, with the mixed audio kept for comparison; switch to turn it off. | The research question is about the background audio; music-only input is also closer to the DEAM training data. Finding: the voice was inflating predicted energy (+0.28 → −0.02). |
| **CLAP text encoder** (same pretrained model) | Zero-shot description of the background music: compare its embedding with 9 written descriptions ("tense dramatic cinematic music", ...), per window and overall. | Describes the music in words for creators (survey Q15) without any new model or training. |
| **PyTorch building blocks** (LSTM, MultiheadAttention, LayerNorm, Linear) | Designed and trained my own **emotion head**: BiLSTM (128 units per direction) → self-attention with padding mask + residual connection + LayerNorm → 2 outputs with tanh. Masked MSE loss, Adam, dropout 0.3, early stopping. Saved as `c4_emotion_head.pt` (`bilstm_attention_v1`). | This is the trained, original model of the component. It predicts continuous valence/arousal per window using the context of the whole sequence. |
| **DEAM dataset** (music with emotion annotations) | Own preparation: used only the annotated regions, windowing identical to the backend, label = average of the dynamic ratings in each window, checked the real label scale, **split by song** to prevent leakage, embeddings computed once and stored on Drive. | Training data must match how the backend sees YouTube audio, and an honest test needs songs the model never saw. |
| *(none: my own experiment)* | **Baseline + ablation**: mean predictor, closed-form ridge regression (alpha chosen on validation), BiLSTM, BiLSTM + attention, all on the same test songs with RMSE, MAE, Pearson and CCC. Fixed seed, logged hyperparameters, loss curves and comparison table. | Shows each part of my model is worth adding (mean CCC 0.682 → 0.703 → 0.723). |
| *(none: my own design)* | **Measured audio problems**: voice vs. background loudness per window (dB), "background too loud under the narration", distortion (clipping), dead air. | Checkable, explainable detection of the problems viewers report most (survey Q13); functional requirement "excessive loudness / distortion". |
| *(none: my own design)* | **Fusion rules R1–R9** combining Part 1 (music emotion + measured problems) with C1 transcript sections, C2 knowledge gaps and C3 comments; **relative thresholds** (each video compared with its own average); mood–content mismatch rule; confidence scoring (0.5 + 0.2 per agreeing signal, max 0.95); severity upgrades; merging into one card per problem; plain-language evidence and a YouTube link at the right moment; descriptive summary per section. | The prescriptive part of the research gap: turning analytics into concrete, explainable advice for creators. |
| *(none: my own design)* | **Segment-level validation**: agreement of flagged sections with negative viewer comments, an exact random baseline and the lift over chance. | The core claim of the research gap: flagged segments must be checked against what viewers actually react to. Demonstrated on dummy comments; real evaluation once C3 is connected. |
| *(none: my own design)* | **Two-part architecture**: Part 1 (audio analysis, descriptive) and Part 2 (recommendations, descriptive + prescriptive) with separate endpoints, pages and collections. | Part 2 is where the other components plug in; only its inputs change at integration. |
| **yt-dlp + ffmpeg** (download tools) | Download only the first 3 minutes of audio; check the result is complete; retry up to 3 times on dropped connections; delete temporary files automatically. | Long videos stay fast, and unstable connections never cause a silent half-analysis. |
| **FastAPI, Streamlit, Plotly, MongoDB** (frameworks) | My API (`/analyze`, `/analyses`, `/analyses/{id}`, `/health`) with the agreed JSON contract, MongoDB caching by `video_id`, clear error messages; my UI: emotion timeline with highlighted sections, valence–arousal map, dummy-data panel, recommendation cards, JSON download. | A working end-to-end demo that the final team dashboard can consume as clean JSON. |
| *(none: placeholders for teammates' work)* | Dummy C1 transcript sections, C2 knowledge gaps and C3 comments (per demo video + default), isolated in `mock_loader.py` and marked `"mock": true`. | Lets the fusion be built and demoed before C3 and the knowledge graph are ready, and makes swapping in real data a one-file change. |

**In one sentence for the viva:** *Demucs and CLAP are pretrained tools I use frozen; I built the emotion model on top of CLAP (trained and evaluated against a baseline), and everything that turns the separated audio into findings and advice (the loudness measurements, the fusion rules with the other components, confidence, evidence and the validation against viewer comments) is my own design.*
